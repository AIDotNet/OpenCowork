# TaskList 改造前后基线度量

配套方案:[task-list-redesign.md](task-list-redesign.md)。

本文件是**测量协议 + 数据记录表**。改造前跑一遍填「改造前」列,第 8 步验证时用完全相同的提示再跑一遍填「改造后」列。两次必须用同一组 Provider 和同一组提示,否则数据不可比。

## 为什么需要基线

本次改造的核心目标(提示词质量、任务粒度)无法用 typecheck / lint 验证。没有基线就无法区分「提示词改动生效了」和「这次刚好抽到一个愿意多写几条的模型」。因此第 1 步必须先于所有代码改动完成。

## 测量协议

- **Provider**:至少 2 个,覆盖两种不同的工具调用实现(建议 Anthropic Messages + OpenAI Responses)。记录具体模型名与版本。
- **重复次数**:每个提示每个 Provider 跑 3 次,取中位数。单次结果噪声很大,不要只跑 1 次。
- **会话隔离**:每次新建会话。同会话第二轮会看到 `<system-reminder>` 里的既有任务,污染「首次建列表」的测量。
- **模式**:固定用 `cowork` 模式。`clarify` 模式的提示词会把规划压力导向 Plan 文件,不适合测任务清单。
- **工作目录**:固定指向本仓库,保证三个提示都有真实代码可读。

## 三个固定提示

三个提示分别覆盖不同的任务分解触发路径,不要替换。

**P1(跨文件重构类)** — 检验能否把一个宽泛目标分解成有序步骤:

```text
把 src/renderer/src/lib/agent/dynamic-context.ts 里的 runtime reminder 构建逻辑抽成独立模块,
拆分 tasks / plans / goals / selected files 四个片段的构建函数,并保持现有注入顺序不变。
```

**P2(先调研后动手的排查类)** — 检验能否区分「调研」与「修复」两个阶段,以及是否会写出无完成判据的条目:

```text
Agent 在团队模式下创建的任务有时不会出现在任务板上,查清原因并修掉。
```

**P3(显式列出 5+ 子需求的实现类)** — 检验是否会把用户已经列好的清单原样落成任务(这是最低要求,做不到说明工具或提示词有硬阻塞):

```text
给 CLI 的任务列表组件加五个能力:1) 按状态分组显示;2) 折叠已完成项;
3) 显示任务依赖关系;4) 支持键盘上下选中;5) 选中后按 d 显示任务详情。
```
