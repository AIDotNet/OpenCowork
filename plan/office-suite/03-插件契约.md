# 03 · 插件契约 v2：让 Office 成为一个内置插件

> 目标：`com.opencowork.office` 是 `resources/extensions/office/` 下的一个**普通扩展**，
> 只不过随包发布。它能做的每一件事，第三方扩展也能做（在沙箱档位内）。
> 反过来说 —— 只要 Office 还需要往核心代码里塞特例，插件契约就没设计好。

---

## 1. 现有契约缺什么

`ExtensionManifest`（`src/shared/extension-types.ts:80-104`）今天能贡献
工具 / 结果渲染器 / skills / agents / commands / MCP / 配置 / 网络白名单 / 状态目录。

**缺三类**：

1. **文件类型处理器** —— 没有任何字段能到达 `viewerRegistry`
2. **原生 UI 挂载** —— 扩展 UI 只能是 iframe 里的工具结果卡片
3. **带生命周期的会话** —— 扩展是无状态的"调一次工具返一个结果"

第 2 条的后果已经在代码里显形了：`ExtensionToolResultCard.tsx:757-800`
硬编码了 5 个 `luckin_*` React 组件作为 fallback ——
一个内置扩展的实现细节泄漏进了核心渲染器。**Tier-1 信任档就是这个缺陷的正解**，
落地时顺手把 my-coffee 的特例从核心里拆掉。

## 3. 信任分层（核心架构决策）

现状是**单一档位**：所有扩展 JS 跑主进程 Node `vm`，UI 只能进 iframe。
这既挡不住恶意扩展（`vm` 逃逸 = 主进程权限），又让内置扩展做不了正经 UI。
两头不到位。改成三档：

| 档位            | 谁能用               | UI 挂载                                                   | 模型访问                                                     | 代码执行       |
| --------------- | -------------------- | --------------------------------------------------------- | ------------------------------------------------------------ | -------------- |
| **`builtin`**   | 随包发布             | **ES module 直挂**，共享 React/Zustand，可用 canvas/WebGL | 完整 `doc/*`                                                 | 与渲染层同权限 |
| **`signed`**    | 官方签名的第三方     | ES module 直挂，但走受限 API 门面                         | `doc/*`，限声明的扩展名                                      | 同上           |
| **`sandboxed`** | 默认（任何本地安装） | `<iframe sandbox="allow-scripts">` + postMessage          | `doc/*` 代理，**强制限声明的扩展名**，只读默认，写需用户授权 | 现有 `vm` 沙箱 |

三条硬约束：

1. **文档解析永远在 C# worker**，绝不在扩展 JS 里。
   不可信文件的解析攻击面（ZIP 炸弹 / XXE / 畸形 XML / 深嵌套）必须挡在进程边界外。
   `documentProviders[].model.provider` 只允许 `"native"`（指向 worker 模块）
   或 `"worker"`（扩展自带的 sidecar 进程），**不允许 `"js"`**。
2. **`trust` 不由清单自述决定**。清单里写了也不算数 ——
   由安装来源判定：`resources/extensions/` 下的 = `builtin`，
   校验通过的签名包 = `signed`，其余一律 `sandboxed`。
   否则 `"trust": "builtin"` 就是一行提权。
3. **Tier-2 的 `doc/*` 代理必须在 main 侧做扩展名归属校验**，
   不能信任渲染层传来的 `docId`。

### Tier-2 的文档 API 门面

沿用 `ExtensionToolResultCard.tsx:199-214` 已验证的 postMessage 模式
（`event.source` 校验 + source tag 校验 + 高度钳制），扩展为文档协议：

```
host → frame:  { type: 'doc:snapshot', docId, revision, model }
               { type: 'doc:changed', docId, revision, effects }
frame → host:  { type: 'doc:apply', docId, baseRevision, ops }
               { type: 'doc:request', scope }
               { type: 'resize', height }
```

顺手修掉现有的一个小问题：host 目前用 `targetOrigin: '*'` 投递 props
（`ExtensionToolResultCard.tsx:209`）。opaque-origin iframe 下应传 `'null'`。

## 4. `DocumentHost` 解析顺序

```
DocumentHost(path)
  1. ext = extname(path)
  2. providers = viewerRegistry.getDocumentProviders(ext)
       ← 来源：内置注册 + 已启用扩展的 documentProviders
  3. 过滤：扩展未在当前项目激活 → 剔除
           （复用 extension-store.ts:76-88 resolveEffectiveActiveExtensionIds）
  4. 排序：priority desc，同分则 builtin > signed > sandboxed
  5. 选中 provider → doc/open → 按 ui.type 挂载 module 或 iframe
  6. 全部失败 → 回退到现有 fallback（Monaco / 二进制卡片）
```

用户可在设置里为某个扩展名**钉住** provider（`office` vs 第三方）。

## 6. 目录形态

```
resources/extensions/office/
  extension.json                 # schemaVersion 2
  engines/
    sheet/index.js               # canvas 网格（Tier-1 ES module）
    slide/index.js               # SVG 形状树
    word/index.js                # 保真页 + 结构编辑器 双模
  panels/inspector.js
  cards/doc-edit.html            # 工具结果卡片（iframe）
  skills/                        # 复用现有 skills 同步机制
  README.md
```

worker 侧对应 `sidecars/OpenCowork.Native.Worker/Modules/Document/`：
`DocumentModule.cs` / `DocumentSessionStore.cs` / `OoxmlPackage.cs` /
`SheetAdapter.cs` / `WordAdapter.cs` / `SlideAdapter.cs` / `PatchEngine.cs` /
`RenderService.cs` / `FileGuard.cs`。

**这里有一处刻意的不对称，需要认可**：Office 扩展的**模型层**是编译进 worker 的
（`model.provider: "native"`），只有 **UI 层**在扩展目录里。
理由：文档解析必须在进程边界内、必须 AOT 编译、必须能被单测覆盖不变式。
第三方扩展想自带模型层，走 `model.provider: "worker"` 起自己的 sidecar 进程。
这和 channel plugins 编译进主程序是同类取舍，但比它好 —— 至少 UI 和工具是真插件。

## 7. 管理界面：Office 插件在哪儿显示

现有扩展只有**两个展示面**：

| 位置            | 组件                                                         | 能做什么                                                    |
| --------------- | ------------------------------------------------------------ | ----------------------------------------------------------- |
| 设置 → 扩展     | `ExtensionPanel.tsx`（668 行），挂在 `SettingsPage.tsx:3890` | 安装 / 启用停用 / 配置 / 卸载 / 打开目录 / 查看捆绑资源统计 |
| 输入框 `+` 菜单 | `SkillsMenu.tsx:725-757`                                     | 列出已启用扩展，**按项目**激活/取消，跳转到设置页           |

Office 作为 `resources/extensions/office/` 下的扩展，会被
`EnsureBuiltinExtensions`（`ExtensionManagementStore.cs:375-448`）在首次 `list` 时
复制到 `~/.open-cowork/extensions/` 并 `enabled: true`，因此**两处都会自动出现**，
无需额外代码。

### 7.1 【阻断性】激活作用域是按项目的，文档查看器不能这样

```ts
// extension-store.ts:76-88 resolveEffectiveActiveExtensionIds
// activeExtensionIdsByProject[projectKey] 默认是空数组
```

扩展"启用"是全局的，但"激活"是**按项目**的，且**默认不激活** ——
必须用户在 `SkillsMenu` 里手动勾。

对工具类扩展这是对的（不希望每个项目都塞满工具）。
但对**文档查看器是错的**：用户在一个没勾 Office 的项目里双击 xlsx，
会得到"无可用查看器"。这是不可接受的回归。

**结论：贡献点必须按类型区分作用域，不能一刀切。**

| 贡献点                  | 作用域                      | 理由                                   |
| ----------------------- | --------------------------- | -------------------------------------- |
| `tools`                 | 项目级激活（保持现状）      | 工具进 prompt，要控制数量              |
| `mcpServers`            | 项目级激活（保持现状）      | 同上                                   |
| **`documentProviders`** | **全局，随 `enabled` 生效** | 文件能不能打开不该取决于当前在哪个项目 |
| **`renderEngines`**     | **全局**                    | 引擎是环境能力，与项目无关             |
| `panels`                | 项目级激活                  | 占用界面空间                           |
| `commands`              | 项目级激活                  | 占用快捷键与命令面板                   |

落地时 `DocumentHost` 的解析顺序（§4 第 3 步）要改：
`documentProviders` **只过滤 `enabled`，不过滤项目激活状态**。
§4 里那句"扩展未在当前项目激活 → 剔除"仅对 `panels`/`commands` 成立。

### 7.2 `ExtensionPanel` 需要补的展示

Office 会带来现有扩展没有的两类信息，面板里应体现：

- **接管的文件类型**：列出 `documentProviders[].extensions`，
  以及"当前由谁接管 `.xlsx`"（多个扩展竞争同一扩展名时，
  按 §4 的 priority + trust 排序，用户可钉住）
- **渲染引擎状态**：`renderEngines` 的探测结果
  （"未安装 / 已探测到系统 soffice 25.2 / 已下载"）+ 下载按钮

这两块是 `documentProviders` / `renderEngines` 独有的，
`ExtensionPanel` 现在只展示 skills/agents/commands/mcp 的计数
（`formatBundledCounts`，`ExtensionPanel.tsx:31`），需要扩展。

### 7.3 顺带修：`interface` 元数据是死的

`ExtensionInterfaceMeta`（`extension-types.ts:72-78`）的
`displayName` / `category` / `brandColor` / `defaultPrompt`
**在 `src/` 和 `sidecars/` 里没有任何消费方**（已全仓 grep 确认）。

五个内置扩展全都认真填了它 —— creative-production 写了 3 条 `defaultPrompt`、
hyperframes 写了 4 条、my-coffee 写了中文的 2 条 —— 但没有任何界面读取。
`SkillsMenu.tsx:746-747` 显示的是 `manifest.name` 和 `extension.id`，
不是 `interface.displayName`。

这说明当初设计了"扩展在 composer 里有品牌化入口 + 推荐提示词"这个功能但没接完。
做 v2 时应当一并接上：`SkillsMenu` 用 `displayName`/`brandColor` 渲染，
`category` 用于分组，`defaultPrompt` 做点击即填的建议条。
Office 插件会直接受益（"帮我把这张表按项目分组汇总"之类）。
