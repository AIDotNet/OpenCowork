# 01 · 现状分析：Office 文档预览与编辑

> 结论先行：当前实现**不是"保真度不够"，而是架构上不具备保真的可能性**。
> 文档在系统里的类型是 `string`，而 OOXML 是一个 ZIP 包。这个类型错误往下传导，
> 导致了保存毁档、无法实时编辑、Agent 完全读不到文档三个后果。

---

## 1. 核心链路

所有预览走同一条链：

```
openFilePreview(path)                       ui-store.ts:1750
  └ buildFilePreviewState()                 ui-store.ts:738-896   ← 扩展名 → viewerType 判定表
      └ PreviewPanel                        PreviewPanel.tsx:125  ← Tab 条 / 面包屑 / 工具栏
          └ viewerRegistry.getByType()      viewer-registry.ts:36
              └ <Viewer {...ViewerProps} /> PreviewPanel.tsx:685-706
```

`ViewerProps` 是全部问题的根：

```ts
// src/renderer/src/lib/preview/viewer-registry.ts:4-16
export interface ViewerProps {
  filePath: string
  content: string // ← 只有文本。二进制格式无法通过这里传递
  viewMode: 'preview' | 'code'
  onContentChange?: (content: string) => void
  onSave?: () => void | Promise<void>
  fileVersion?: number // ← 变化即"整份重读"
  // ...
}
```

因为 `content` 是 `string`，所有二进制查看器（xlsx / docx / pdf / image / video / font）
都**绕过注册表契约自己去拉字节**（`FS_READ_FILE_BINARY` → base64）。
`PreviewPanel.tsx:94-104 shouldReadPreviewText()` 专门为此开了个白名单跳过文本读取。

也就是说：注册表的契约对 Office 文档是**失效的**，每个查看器自己重新发明了一遍加载逻辑，
而且都只能做"整份读 → 整份写"。

## 2. 各格式实际保真度

| 格式                          | 实现                                      | 能看到什么           | 能编辑吗                                  |
| ----------------------------- | ----------------------------------------- | -------------------- | ----------------------------------------- |
| `.xlsx .xls .xlsm .xlsb .ods` | SheetJS → `string[][]` → HTML `<table>`   | **只有单元格文本**   | 能改，但**保存即毁档**（见 §3）           |
| `.csv .tsv`                   | 手写解析器 `spreadsheet-viewer.tsx:10-60` | 文本网格             | 能改；`.tsv` 存回变逗号分隔，全空行被丢弃 |
| `.docx .docm .dotx`           | mammoth → HTML + `prose` CSS              | 段落与基本内联样式   | **只读**                                  |
| `.doc .rtf .odt .ott`         | `office-online-viewer`                    | **本地文件：零预览** | 否                                        |
| `.pptx .ppt .pps .ppsx .odp`  | `office-online-viewer`                    | **本地文件：零预览** | 否                                        |
| `.pdf`                        | react-pdf / pdfjs 5.4                     | 单页 + 前后翻页      | 只读                                      |

### 2.1 `office-online-viewer` 是个死胡同

```ts
// office-online-viewer.tsx:7-31
function isPublicHttpUrl(value: string): boolean {
  return /^https:\/\/\S+/i.test(value)
}
// 只有公网 HTTPS URL 才会渲染 iframe：
//   https://view.officeapps.live.com/op/embed.aspx?src=...
```

本地路径与 SSH 路径一律落到"需要公网 URL"提示卡 + "用系统应用打开"。
**这意味着 `.pptx` 在应用内没有任何预览能力**，`.doc` / `.rtf` 同理。
而且即使有公网 URL，也等于把用户文档上传给微软——对私有文档不可接受。

### 2.2 docx 查看器自己承认了保真问题

`docx-viewer.tsx:76-78` 常驻一条提示条 `preview.docxCompatibilityHint`
（"已转换为网页内容，排版可能与 WPS 不同"）。mammoth 的语义是
**"docx → 语义化 HTML"**，它主动丢弃分页、页眉页脚、字体度量、文本框、
编号续接、域、批注、修订。它不是保真渲染器，用它做保真是方向性错误。

## 3. 【严重】xlsx 保存会摧毁工作簿

这是当前最高优先级的缺陷，且**用户完全无感知**。

**加载**（`spreadsheet-viewer.tsx:64-80`）：

```ts
const rows = XLSX.utils.sheet_to_json(sheet, { header: 1, defval: '' })
data.set(
  name,
  rows.map((r) => r.map(String))
) // ← 一切变成字符串
```

**保存**（`spreadsheet-viewer.tsx:93-104`）：

```ts
const wb = XLSX.utils.book_new() // ← 从零新建工作簿
for (const [name, rows] of sheetsData) {
  const ws = XLSX.utils.aoa_to_sheet(rows) // ← 只写文本
  XLSX.utils.book_append_sheet(wb, ws, name)
}
```

点一次 Save，原文件里以下内容**全部永久丢失**：

- 公式（退化为缓存值，且变成文本）
- 数字 / 日期 / 布尔类型（全部变成字符串，Excel 里显示为左对齐文本并报"数字存储为文本"）
- 单元格样式、字体、填充、边框、数字格式
- 合并单元格、列宽、行高、冻结窗格、筛选器
- 条件格式、**数据验证（下拉列表）**
- 图表、图片、批注、透视表、定义名称、隐藏工作表/行列、VBA 宏

截图中那份"工时补录"模板正是**下拉列表驱动**的（"如项目下拉列表没有你想要的项目，也可手动填定"），
表头还带合并与说明行。用当前查看器编辑并保存，这份模板会直接报废。

配套缺陷放大了风险：

- `spreadsheet-viewer.tsx:236,247`：工作簿模式下 undo/redo 直接 `return`，**改错了退不回去**
- 工作簿编辑**不设置 tab 的 `modified` 标记** → 关闭标签页时的"未保存"确认框永远不触发
- `PreviewPanel.tsx:611-620` 的全局 Save 对工作簿是禁用的，只有网格内那个小 Save 生效
- 表格是纯 `<table>`，**无虚拟化**——1 万行就是 1 万个 DOM 行

## 4. Agent 侧：完全够不到文档

用户提到的"tool 的多功能支持"，现状接近于零。

**读被显式封禁**：

```csharp
// sidecars/OpenCowork.Native.Worker/Modules/File/FileTools.cs:49
private static readonly HashSet<string> TextReadBlockedExtensions = new(...)
{ ".pdf", ".doc", ".docx", ".xls", ".xlsx", ".ppt", ".pptx", ... };
// :57 GrepBinaryExtensions —— Grep 同样跳过
```

- `Read` 对 Office 文件直接拒绝
- `Grep` 跳过 Office 文件
- `use-chat-actions.ts:538-575` 的 `SELECTED_FILE_TEXT_READ_BLOCKED_EXTENSIONS`
  让附件栏里的 Office 文件也不会被读进 prompt

**唯一的文档解析**：`FileDocumentTools.cs:53-122`（`fs/read-document`）——
只支持 `.docx`，只做 `word/document.xml` 纯文本抽取，
而且**它不是 Agent 工具**，只被宠物功能和皮肤商店调用（`pet-memory.ts:37,92`）。

**Agent 现在的绕行路线**是 `resources/skills/{xlsx,docx,pdf,excel-processor,csv-pipeline}`——
Python 脚本 + openpyxl / LibreOffice，靠 `Bash` 跑。这条路能用，但：
它在应用外操作文件，UI 完全不知情，改完必须整份重读，
和"实时编辑更新"是互斥的。

## 5. 插件系统：表达不了这件事

扩展清单（`src/shared/extension-types.ts:80-104`）**今天能贡献**：
工具（http / js）、工具结果渲染器与组件（iframe）、skills、agents、
slash commands、MCP servers、配置项、网络白名单、状态目录、composer 元信息。

**今天不能贡献**（不存在贡献点）：
**查看器 / 文件类型处理器**、面板与视图、菜单项、设置页、快捷键、
文档模型、任何带生命周期的会话。扩展 UI 只能出现在工具结果卡片里。

三个具体障碍：

1. **`viewerRegistry` 对扩展完全封闭。**
   它本身是个运行时 `Map` + `register()`，**接口天生就支持动态注册**，
   但唯一调用者是 `registerAllViewers()`（`register-viewers.ts:69`），
   没有任何清单字段能到达它。这是全代码库**最接近可扩展的接缝**。

2. **扩展名 → viewerType 判定表存在两份且已经分叉。**
   `ui-store.ts:854-867` 与 `register-viewers.ts:70-218`。
   前者把 https 开头的 `.docx/.xlsx` 路由到 `office-online`，后者根本没把
   `.xls/.xlsx` 列进 `office-online`。**任何新格式都要改两处**——
   这是插件化之前必须先还的债。

3. **`ExtensionComponentRenderer` 里硬编码了 5 个 `luckin_*` React 组件**
   作为回退（`ExtensionToolResultCard.tsx:757-800`）。
   这是"内置扩展想要原生 UI，但机制不存在"打的补丁——
   一个内置扩展的实现细节泄漏进了核心渲染代码。

### 5.1 沙箱强度不足以承载文档引擎

扩展 JS 跑在**主进程的 Node `vm`** 里（`extension-js-runtime.ts:343-393`）：
`require/module/process/fetch` 被置空，`codeGeneration.wasm = false`，1s/30s 超时。

`vm` 是**隔离，不是安全边界**——逃逸即获得主进程权限。
文档解析要处理不可信文件（ZIP 炸弹、XXE、畸形 XML、超深嵌套），
攻击面极大。**文档解析绝不能放在扩展 JS 里。**

## 6. 工具架构摩擦

（影响"tool 多功能支持"的落地成本，必须先知道。）

- 渲染层的工具**全是 schema 空壳**，`execute` 一律返回
  "已迁移到 .NET Native Worker"（`fs-tool.ts:5-9,28`）。
  真正执行在 `AgentRuntimeNativeToolExecutor.cs`（2280 行）。
- `src/main/ipc/js-agent-runtime.ts` **已不存在**，
  实为 `native-agent-runtime.ts`（纯传输 shim，零工具逻辑）。**CLAUDE.md 此处已过时。**
- **cron 分叉了一份 schema**：`cron-agent-background.ts:78`
  `SUPPORTED_BACKGROUND_TOOLS`（10 个名字）、`:58` 同样的 10 个名字再列一遍、
  `:1157` `BACKGROUND_TOOL_DEFINITIONS` 把 schema 又抄一遍。
  漏加会被 `:1311` 静默过滤掉，**不报错**。
- 结论：**新增一个工具至少写两遍，要进 cron 就三遍。**
- 工具要驱动 UI，必须往
  `renderer-tool-bridge.ts:31-38` 那个**硬编码 6 项白名单**里加方法：
  `ask-user/request`、`plan/ui-update`、`team/ui-update`、
  `subagent/ui-update`、`browser/tool-request`、`canvas/tool-request`。
  没有通用通道。
